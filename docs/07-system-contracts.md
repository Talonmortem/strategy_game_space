# Контракты между системами

Статус DRAFT, версия 0.1 от 2 ноября 2026 года. Общие требования и допущения приведены в [основах проекта](00-project-foundation.md), открытые решения — в [реестре решений](10-open-decisions.md).

### Единый источник состояния

Экономика владеет реестром физических запасов, денежных счетов и населения. Военные системы запрашивают снабжение и сообщают о потерях через согласованные изменения. Политика использует исполнение потребностей и историю потерь. UI и игровой ИИ читают разрешённые представления одного состояния. Дублировать ресурс армии в отдельной от экономического учёта переменной нельзя.

Контроль территории, юридическое владение и доступ к складу проверяются независимо. Захваченный склад сначала меняет режим доступа; судьба его содержимого определяется событием захвата. Разрушение записывает физические потери, присвоение — передачу владельца, реквизиция — изменение получателя. Ни одно из этих действий не создаёт второй экземпляр товара.

### Минимальные контракты

| Контракт | Вход | Выход | Существенное правило |
| --- | --- | --- | --- |
| `SubmitCommand` | ID партии, ID приказа, отправитель, тик, тип, параметры | Квитанция, статус, код ошибки | Повторная доставка того же ID возвращает прежний результат |
| `QueryState` | Тик или текущий снимок, наблюдатель, область | Состояние и разрешённые пояснения | Не раскрывает невидимые данные при обычном игровом доступе |
| `ReserveResources` | Получатель, назначение, количество, срок | ID резерва, удовлетворённая часть | Один физический запас не резервируется дважды |
| `ReserveBundle` | Согласованный набор товара, денег, топлива, транспорта и вместимости | Общий ID резерва либо полный отказ | Недостаток одного обязательного ограничения отменяет создание всего набора |
| `RequestSupply` | Потребитель, товар, количество, период, приоритет | Фактическая доставка и причины недопоставки | Заявка не равна полученному ресурсу |
| `EvaluateRoute` | Источник, назначение, доступ, объём | Путь, срок, ограничения, стоимость | План не гарантирует возможность отправки к будущему моменту |
| `ApplyControlChange` | Объект, прежний и новый контролёр, причина | Изменения доступа и события | Учитывает повреждения, гарнизон, открытые грузы и стройки |
| `ExplainConstraint` | Объект, действие или показатель | Код причины, связанные сущности, данные прогноза | Человеческий текст строится по локализуемому шаблону |
| `SaveSnapshot` | Согласованное состояние на границе тика | Версионированный снимок | Сохраняет резервы, грузы, очереди и генераторы случайности |

Это требования к интерфейсам, а не готовые библиотеки. Конкретные типы выбираются после решения о языке. Общие поля и смысл сохраняются при смене технологического кандидата.

Пример предлагаемого формата приказа:

```json
{
  "schema_version": 1,
  "game_id": "scenario_blockade_01",
  "command_id": "player_1_000042",
  "actor_id": "empire_1",
  "actor_sequence": 42,
  "execute_at_tick": 240,
  "type": "SetSupplyPriority",
  "payload": {
    "consumer_id": "facility_17",
    "good_id": "good.fuel",
    "priority": "essential"
  }
}
```

Приказ с уже прошедшим тиком отклоняется с `STALE_TICK`, если отдельный режим повтора не определяет другое поведение. Приказы на уничтоженную цель получают `ENTITY_MISSING`. Повторение ID с другим содержимым получает `COMMAND_ID_CONFLICT`. Ошибка при проверке не оставляет частично списанных ресурсов. Полный ключ порядка: `execute_at_tick`, `actor_id`, `actor_sequence`. Распределение физического дефицита определяется экономической политикой, не временем выполнения потока.

Квитанция принятия в очередь отличается от результата исполнения. При выполнении на назначенном тике условия проверяются снова; изменившаяся цель или недоступный ресурс дают явный отказ исполнения. Реестр принятых и исполненных ID, последовательности отправителей и результаты дедупликации сохраняются или восстанавливаются из согласованного журнала. После загрузки повтор старого приказа возвращает прежний результат. CLI и семантические действия UI используют тот же конверт и обработчик; непосредственное изменение рабочего состояния в обход команд не является обычным интерфейсом инструмента.

### Общие пограничные случаи

При потере цели в пути военная или торговая группа остаётся существующей сущностью. Пересчитываются доступные последующие действия. Перегруженный склад не принимает больше доступной вместимости; груз остаётся в транспортном хранении или перенаправляется по явному правилу. Изменение принадлежности территории не отменяет уже произошедшие затраты. Сохранение во время многопоточного расчёта использует последний согласованный снимок либо дожидается границы тика.

Доступ к следующему участку пути использует контроль и дипломатические правила, действующие на момент начала участка. Уже находящийся в переходе груз завершает текущий участок; его дальнейшая судьба определяется правилами прибытия и доступностью следующего узла. Блокада может сделать разгрузку недоступной, не телепортируя груз на склад. Это рабочее правило для V0; интердикция внутри перехода требует отдельной модели позже.

Товар, произведённый в экономическом периоде, становится доступен новым потребителям в следующем периоде. Продажа или отправка продукции не может выполнить всю производственную цепочку за один тик за счёт порядка обхода предприятий. Финальный порядок фаз экономического раздела применяется ко всем модулям и уточняется единым изменением, а не локальной перестановкой.

### Объяснения и прогнозы

Каждый значимый остановившийся процесс сообщает код причины: нет сырья, работников, энергии, денег, транспорта, разрешённого пути или безопасного доступа. UI показывает ограничивающий фактор и связанные объекты. Прогноз запасов указывает условия неизменности производства и потребления; он не представляется как точное знание будущих действий противника.

История изменения показателей хранится в пределах настроенного окна. Полный мировой журнал каждой мелкой операции не обязателен в обычной партии; диагностический режим включает его для выбранных сущностей и сценариев. Это ограничивает объём данных при сохранении способности объяснить причинную цепочку.

### Военные действия и граница экономического периода

Рабочее правило V0: контроль и состояние блокады фиксируются на начале экономического периода после применения назначенных событий. Результат боя или захвата, рассчитанный в этом периоде, меняет доступ со следующего периода. Поэтому два потока не могут по-разному решить, разрешена ли одна и та же разгрузка. Внутри текущего периода боевой расход берётся из уже доступных запасов; новый выпуск текущего периода не используется.

Объявление войны и мирный договор становятся назначенными событиями начала периода. Движение не порождает мгновенную доставку через все узлы пути. При необходимости более частого боевого шага его результаты публикуются на согласованной границе экономического периода; изменение этой задержки является изменением правил, а не оптимизацией.

Открытые транспортные развилки: расчёт платы за частично выполненный или отменённый после отправки рейс; окончательная судьба груза при невозможности разгрузки; срок и способ возврата. До реализации соответствующего перехода эти правила нужно дополнить. Полный возврат незаработанного escrow при окончательной потере груза не означает бесплатную отмену уже оказанной услуги перевозки.
