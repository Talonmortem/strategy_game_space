# Проверки порядок разработки и работа агентов

Статус DRAFT, версия 0.1 от 2 ноября 2026 года. Общие требования и допущения приведены в [основах проекта](00-project-foundation.md), открытые решения — в [реестре решений](10-open-decisions.md).

| Код | Проверяемое правило | Ожидаемый результат |
| --- | --- | --- |
| FX01 | Баланс товаров | Конечный запас равен начальному плюс поступления и производство минус расход, отправки и явные потери |
| FX02 | Резервы | Два приказа не используют один и тот же материал; отмена освобождает только оставшийся резерв |
| FX03 | Перевозка | Груз имеет одно местонахождение и владельца; `awaiting_unload` ещё не увеличивает склад и не выплачивает escrow; `delivered` делает это однократно |
| FX04 | Мощность маршрута | Отправленный и принятый объём не превышает применимую вместимость |
| FX05 | Блокада | Перекрытый доступ прекращает соответствующие доставки по правилу участка; местные запасы продолжают существовать |
| FX06 | Возобновление снабжения | После открытия пути груз проходит реальное время доставки, затем производство получает входы |
| FX07 | Выгода специализации | При равных исходных ограничениях и надёжных поставках профильный выпуск выше у специализации |
| FX08 | Устойчивость разнообразия | При предусмотренном перебое автономная компоновка дольше сохраняет критическую работу |
| FX09 | Десант | Армия без транспорта не перемещается; без снабжения теряет доступные возможности по правилам |
| FX10 | Контроль и мир | Возвращение оккупированной территории не восстанавливает разрушенные объекты бесплатно |
| FX11 | Разведка | UI и ИИ не видят новые изменения вне наблюдения |
| FX12 | Сохранение | Непрерывный и разделённый загрузкой прогон дают одинаковое авторитетное состояние |
| FX13 | Повтор приказов | Повторный `command_id` не дублирует эффект |
| FX14 | Детерминированный прогон | При одинаковой сборке, контенте, seed и приказах совпадают хеши контрольных тиков |
| FX15 | Денежный учёт | В предлагаемой закрытой модели сумма всех счетов вместе с escrow сохраняется после инициализации; эмиссия и изъятие требуют отдельного изменения спецификации |
| FX16 | Ликвидность и развитие | Рост мощностей и основание колонии не создают необъяснимых денег и не скрывают системную остановку оборота |
| FX17 | Автоматизация | Делегированный бюджет и ручные резервы соблюдаются |
| FX18 | Первый игровой сценарий | Игровой ИИ способен поддерживать хозяйство и завершать осмысленную операцию |

Для сравнительных FX07 и FX08 фиксируются одинаковые население, стартовые материалы, денежный бюджет, технологии, доступные площадки и горизонт измерения. Отдельно учитываются стоимость транспорта, инфраструктуры, хранения и охраны. Сравниваются полезный выпуск, исполнение критических потребностей и время восстановления; общая стоимость разных товаров считается только при явно фиксированных ценах сравнения.

Успех пары сценариев не доказывает баланс всей игры. Следующий шаг — варьировать расстояние, длительность перебоя, спрос, резерв и местные ресурсы. Должны существовать области, где каждый подход полезен, и промежуточные решения с понятной ценой.

Автоматические проверки дополняются наблюдением за игроком: может ли он объяснить дефицит, найти действие по его устранению, оценить риск специализации и назвать решение, которое изменило исход осады. Эти признаки не заменяются числом написанных тестов.

## Порядок разработки

| Этап | Результат | Зависимости и критерий перехода |
| --- | --- | --- |
| P0 | Зафиксированы формат боя, графика, время и границы движка | Закрыты D01–D04 и выбран сценарий технической проверки |
| P1 | Проверен технологический кандидат | Карта, таблица, кириллица, масштаб, CLI и прогон без окна; записаны результаты |
| P2 | Работает ядро команд и состояния | Стабильные ID, валидация приказов, сохранение, воспроизведение |
| P3 | Работает физическая экономика трёх планет | Товары, рецепты, запасы, стройка, перевозки; проходят FX01–FX08 |
| P4 | Работают простой рынок и общественные последствия | Явные счета, исполнение потребностей, контроль ликвидности; денежная модель выбрана |
| P5 | Работают космические операции и блокада | Флоты, транспорт, столкновение, снабжение; потери отражаются в экономике |
| P6 | Работает наземная операция и завершение конфликта | Регионы, порт, осада, контроль, восстановление и мир |
| P7 | Завершён игровой срез | UI объясняет причины, противник принимает допустимые решения, сценарий имеет начало и конец |
| P8 | Расширяется кампания | Генерация, контент, более глубокие политика и дипломатия по результатам среза |

UI развивается вместе с P2–P7. Нельзя откладывать читаемость до завершения экономики. Простой игровой ИИ начинается с хозяйственных правил в P3; его военные возможности добавляются вместе с соответствующими действиями. Этапы обозначают зависимости, а не обещанные календарные сроки.

В P3 блокада задаётся сценарным событием через общий контракт доступа. Полноценные флоты из P5 используют тот же контракт, поэтому проверка экономики не требует заранее реализовать всю войну.

Подготовка схем и сценариев — полезная работа до реализации. Техническая проверка P1 является будущей отдельной задачей после выбора её условий; в рамках этой версии документа она не выполнена.

## Работа агентов

### Разделение ответственности

Владелец дизайна определяет цели и общие игровые правила. Интегратор поддерживает контракты, порядок фаз и совместимость форматов. Исполнители получают ограниченные модули. Проверяющий сопоставляет изменение со сценарием и ищет нарушения на стыках. Эти роли могут исполняться небольшой группой, не обязательно одновременно отдельными процессами.

В первую очередь можно параллелить определения контента, диагностику, представление UI и проверку уже стабильной логики. Изменения общего состояния, порядка фаз, схем сохранений и распределения ресурсов должны иметь одного интегратора. Каждый исполнитель работает в изолированной ветке или worktree, если репозиторий это поддерживает.

### Шаблон задания

```text
Цель: наблюдаемое изменение поведения игрока или инструмента.
Версия спецификации: точная версия и нужные разделы.
Статус модуля: READY.
Разрешённая область: пакеты и файлы.
Контракты: входы, результаты, команды, события, единицы.
Зависимости: готовые интерфейсы и фиксированные схемы.
Сценарий приёмки: исходное состояние, действия, ожидаемые последствия.
Пограничные случаи: отмена, дефицит, уничтоженная цель, повтор приказа.
Проверки: минимальный набор, устраняющий реальные риски изменения.
Отчёт: что изменено, как проверено, ограничения, нерешённые противоречия.
```

Агент может самостоятельно выбирать структуру локального метода и устранять обычные ошибки в своей области. Он не должен незаметно менять модель владения, вводить новые ресурсы, обходить ограничения для противника или заменять открытый дизайн произвольной формулой. Если неопределённость влияет на контракт, она возвращается в перечень решений вместе с конкретными вариантами.

### Критерий готовности изменения

Изменение собирается, соответствует контракту, проходит обязательный сценарий и не ломает значимые существующие проверки. Новая информация доступна для диагностики; игрок получает необходимое объяснение. При изменении сохраняемого состояния обновляются версия или миграция. После проверки интегратор включает изменение в основную ветку, сохраняя рабочий сценарий.

Конкретные версии зависимостей фиксируются в репозитории. Воспроизводимая сборка включает исходные данные, генераторы производных ресурсов и информацию о версии инструментария. Скачивание новейшей библиотеки без проверки не считается частью обычной игровой сборки.
